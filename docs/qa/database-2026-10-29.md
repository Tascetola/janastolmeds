## 1. Scope

| Change | Changelog | Decision |
| --- | --- | --- |
| Records are never physically deleted. 18 patient, clinical and financial tables have `RECORD_STATUS` (ACTIVE/DELETED), `DELETED_ON`, `DELETED_BY`, `DELETE_REASON`. A `<TABLE>_RECORD_GUARD` compound trigger refuses `DELETE` (ORA-20030), stamps who/when on a soft delete (caller values overruled) and freezes deleted rows, including against restore (ORA-20031). Addenda can never be changed or deleted (ORA-20013). Business-key unique constraints become unique indexes over ACTIVE rows, with plain indexes added for the foreign keys they used to cover. | `120_soft_delete.sql` | DEF-006 |
| HMO settlement is tracked separately. New `JM_HMO_CLAIMS` (claim lifecycle, approved and paid amounts, remittance reference; one live claim per invoice). `JM_INVOICES.HMO_AMOUNT_PAID` is capped at `HMO_AMOUNT`. `HMO` is no longer a patient payment method. New lookups `HMO_CLAIM_STATUS`, `RECORD_STATUS`. | `110_hmo_settlement.sql`, `seed-data/020_lookups.sql` | DEF-009 |

Hiding deleted rows from users is the API layer's job (`JM_*_API` reads filter `RECORD_STATUS = 'ACTIVE'`) and is tested at the API gate.

**Why this was run by hand:** CI rolls back only the changesets a pull request adds that are still pending. The branch was deployed locally first, so CI will find nothing pending and skip that step. This local run is the rollback evidence for this change.

## 4. Defects

| ID | Sev. | Summary | Status |
| --- | --- | --- | --- |
| DEF-006 | S3 | Clinical/financial rows deletable; addenda editable | **Fixed** (product owner decision: soft delete only) |
| DEF-009 | S3 | No place to record HMO remittances | **Fixed** (product owner decision: separate claims table) |
| DEF-011 | S3 | First deploy of `120_soft_delete.sql` failed with ORA-01408: each new foreign-key index was created before the unique constraint already indexing that column was dropped. | **Fixed** in this gate: each `120-ix-*` changeset now follows its `120-uk-*` changeset, so the index is created after the constraint is dropped and dropped before the constraint is restored on rollback. Proven by the full deploy and rollback above. |
| DEF-012 | S4 | `every_not_null_column` reported `JM_VISIT_ADDENDA.ADDENDUM_ID` as accepting NULL. The column is an identity (`GENERATED BY DEFAULT ON NULL`), so a NULL insert correctly receives the next key. A test fault, not a schema fault. | **Fixed**: the insert-copy path skips identity columns. |

Full register: [defects.md](defects.md). Still open from the 28 Oct gate: DEF-005 (→ `JM_CLINICAL_API`) and DEF-008 (→ `JM_CTX_API`), both deferred to the API phase.

**Notes for the API phase:**
- Anonymising a patient record (NDPR) that is already soft-deleted is blocked by ORA-20031. `JM_PATIENT_API` must anonymise before deleting, or the guard needs a controlled exception.
- Synthetic demo data can no longer be removed with `DELETE`. Its removal script must soft-delete it, or be run with the guards disabled in a maintenance window (see [test-data-and-migration.md](test-data-and-migration.md)).
